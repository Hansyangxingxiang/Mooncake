摘要： Master 用 key K 索引对象元数据（ObjectMetadata），并在其中记录副本列表；R1、R2 是同一对象的两个副本，各占一段已分配的内存。对象说明存什么，副本说明有几份、在哪，Store Segment 说明内存从哪来，Store 的 Slice 说明调用方这次传入哪段缓冲区。

上篇中，实例 A 把前缀 KV 的一个分块写入 Mooncake Store（下文简称 Store）。继续跟踪其中 key 为 K 的 4 MiB 对象。这次假设它有两份内存副本，先看其中一份到底占用哪段地址。

从 A 调用 Put 的角度看，这只是“写一个对象”。但在 Mooncake 内部，这个动作经过了好几层结构：Master 以 key 为索引保存对象元数据，元数据记录副本，副本指向一段分配好的内存；客户端把待写数据交给 Store 时，又用 Slice 描述这段缓冲区。

如果把这些结构都笼统理解为“一块内存”，后面的可见性、淘汰、SSD 下沉就会越来越难读。

它们各自回答一个具体问题：

  • 对象：存的是什么？
  • 副本：同一份数据有几份、在哪里？
  • Store Segment：这段内存从哪来？
  • Store 的 Slice：调用方这次传入的是哪段缓冲区？

4 MiB 是整个系列跟踪的单个对象的有效负载。整段前缀可能分成多个对象，分块和并行布局由框架决定。

Master 如何通过 key 找到对象和副本？

应用通过 key 访问对象。对于新 key K，PutStart 成功分配副本后，Master 为 K 建立对象元数据（ObjectMetadata），并在其中记录副本列表。

这份元数据记录对象的身份与生命周期信息：谁发起的写入、什么时候开始、对象多大、数据类型、读保护截止时间，以及由 R1、R2 等副本组成的副本列表。

Master 在运行时维护这份对象元数据。客户端给出 key K 后，Master 先定位 ObjectMetadata，再从副本列表找到各副本；查询返回的是序列化的副本描述和租约信息。

R1、R2：同一对象的两个副本

同一个对象可以有多个副本。为了说清楚，本篇把两份内存副本记作 R1、R2。

R1、R2 可能位于不同存储节点，各自占据一段分配好的内存。它们的内容相同，但地址不同，副本状态也可能不一致——例如 R1 的副本状态已经是 COMPLETE，R2 仍是 PROCESSING。

图注：Master 只在 ObjectMetadata 中记录 R1、R2 的位置与状态；两条虚线表示元数据记录，不是 Master 发出的 4 MiB 数据——两份 4 MiB 有效负载由客户端经 Transfer Engine 分别写入各自的 Store Segment。

对象是否存在，与某一份内存副本是否存在，并不是同一件事。

内存副本被淘汰后，如果仍有可读的磁盘副本，对象仍可能被读取。后面的 SSD 篇用 R3 表示这份独立的磁盘副本。

Store Segment 提供空间，副本只占其中一段

存储节点向集群贡献一段连续内存，Master 侧把它登记为一个 Store Segment：起点、大小、传输端点等。副本就是从这个 Store Segment 的地址空间里分配出来的。

以普通主机内存为例，假设 Store Segment 1 的起点 base = 0x10000000，总长 16 MiB。分配器给 R1 的起点距 base 有 8 MiB，也就是 offset = 8 MiB。R1 的有效范围长 4 MiB。

图注：R1 的起点是 base + offset，结束地址是 base + offset + length，结束地址本身不属于 R1。三个区间在地址上首尾相接。图中长度未按比例绘制，前后两段的占用情况省略。

图里的 offset 用来说明副本在段内的位置。这里的内存副本描述携带 buffer_address_、size_ 和传输端点等信息。客户端在这条路径上可以从副本地址 0x10800000 发起搬运。

到了传输寻址这一步，还要认识 Transfer Engine（TE）侧的 Segment。TE 也有 Segment 概念，但指的是传输侧的地址空间抽象，通常每个进程一个，内部再划分缓冲区，用于把副本地址映射到可传输的注册内存。它和 Master 登记的 Store Segment 不是同一种记录：后者关心“这段空间归谁、还剩多少”，前者用于传输侧的注册和寻址。阅读源码或配置时，要先确认讨论的是哪一层，不能只凭名字把它们直接等同。

Store 的 Slice 描述调用方的缓冲区

Store 的 Slice 描述调用方的一段缓冲区，由指针和长度表示（源码中为 ptr 和 size）。假设 A 用两段各 2 MiB 的本地缓冲区表示 K，PutStart 会把两段长度相加，向 Master 申请 4 MiB 对象的副本空间。

在远程内存搬运路径上，第一段写到 R1 的起点，第二段从 副本起点 + 2 MiB 开始写。这里的 2 MiB 是对象内偏移，图中的 8 MiB 是副本相对 Store Segment 的偏移。输入是两段缓冲区，不等于后端执行两个切片：Transfer Engine 后端会按 task 再决定如何拆成执行片段，见传输生命周期篇。

回到两个具体问题：

只回收 R1，K 还可读吗？ 只要 K 还有另一个可读副本——例如 R2 的副本状态已经 COMPLETE，或存在有效的磁盘副本——B 仍可能读到 K。只有 R1 是最后一份可读副本时，回收它才会让对象进入不可读或清理流程。因此，“R1 的空间被回收”和“K 被删除”不是同一个动作。

后端把一次传输拆成多个 slice，副本数量会变吗？ 不会。后端 slice 是处理一个 task 时拆出的执行片段，不是副本。无论调用方传入几段 Store Slice、后端再拆成几个执行片段，副本仍是 R1、R2 这些独立的数据位置。

空间什么时候能释放？

这比“地址在哪里”更重要。

内存副本持有 AllocatedBuffer。副本被删除时，AllocatedBuffer 析构，通过弱引用找到所属分配器，把空间归还。

这条链上有几个边界：

  • 分配器可以比 AllocatedBuffer 先失效，例如 Store Segment 被卸载。此时析构不再归还，因为分配器自身已经不在了。
  • 副本上的占用计数用于约束特定后台操作和回收。对象元数据直接持有副本，副本持有分配句柄。
  • 客户端拿到的描述符可能仍被在途任务使用，释放空间时要考虑这个时间差。

读租约（lease）约束普通删除与淘汰。细节见读租约篇与淘汰篇。

总结

Master 用 key K 索引 ObjectMetadata，其中记录副本列表；每份 4 MiB 副本占用一个 Store Segment 内的区间，起点和结束地址都能由 base、offset、length 算出。Store 的 Slice 只描述调用方传入的缓冲区；后端如何拆分执行片段是 Transfer Engine 的另一层，副本数量仍按独立存放的位置计。

判断可读性和回收时，要记住两条边界：对象存在不等于某份副本存在，R1 的空间被回收也不等于 K 被删除；内存副本之外还可能有磁盘副本，但本篇主线仍看 R1、R2。
